# Level import, marker duplication and background alignment

Implemented on `bm-level-import-marker-duplicate` and manually accepted together with the multi-level import and object-selection extensions. The user authorized committing the release, an ordinary merge to main and production publication after passing checks. A successful deployment must still be confirmed separately. The initial scope added the three actions below; there is no separate level archive format, cross-map marker transfer, new layer system or backend.

The user extended this same iteration with free region movement and mixed object selection. It supersedes the earlier card-only region movement rule while retaining all import/duplicate/alignment behavior described here. The background remains excluded from object selection; its alignment tool keeps separate gestures. [Current object controls](object-selection.md).

## Import levels

The project burger offers **Import levels / Импорт уровней** for an open project in Preparation. This extends the original single-level import in the same iteration. Resolve existing card/alignment drafts through Save and continue / Discard / Continue editing before opening the file picker. A cancelled picker does nothing. The existing project ZIP parser verifies all supported archive versions, paths, required files, checksums, image decoding, references and compressed/unpacked limits before showing a modal selection. Invalid archives allow choosing another file; failed writes retain the validated selection for retry.

The dialog lists every map as a checkbox in saved map order, initially all selected, with **Select all / Выбрать все**, **Clear selection / Снять выбор**, a selected count and a pluralized **Import N levels / Импортировать N уровней** button. An empty selection cannot be confirmed. Each selected row previews its final destination name; deselection recalculates names for the remaining batch. A single checked map retains the original one-level scenario, including explicit confirmation for a one-map ZIP.

Only selected maps, their background placements, regions, placed entities and reachable Asset images are copied. Map descriptions, region documents, trap checks, statuses, tags, appearance, multi-region bindings and background alignment survive. Project context, unrelated maps/entities/assets and source UI preferences are excluded. The entire subset passes through `independentCopy` once: one common set of map/region/entity/asset ID mappings remaps all placements, checks and document images. A source Entity or Asset shared across selected maps is copied once for the batch, preserving the cross-map association without sharing any ID with existing target data. The dialog counts and warns about excluded placements on unselected maps that share these entities; selecting all maps removes that warning. The current format has no other typed cross-map link field; its validator rejects dangling/unsupported structured references. Ordinary text, relative links and external URLs are not rewritten as object references.

`LevelImportRepository` now exposes `snapshot(projectId)` and `insertLevels(project, copy)`. Insertion reads the target snapshot and verifies its revision inside one IndexedDB readwrite transaction. The combined project is validated against existing format/record limits before adding records. All selected maps append consecutively in source order, using one naming pass against existing and already reserved batch names. The transaction inserts fresh records and advances the existing project's revision/timestamp once; it preserves adventure context, current settings and existing records. Late write errors roll back every map, entity, placement and asset in the batch. Repeated read/confirmation and selection/cancel actions are blocked during validation/saving. Cancellation before confirmation writes nothing. The first selected map's background is prepared before writing, so a decode failure cannot leave a stored batch with a failed initial transition; all archive images already passed validation.

The name preview uses a consistent target snapshot read while validating the ZIP. Confirmation rejects a changed target revision instead of silently using different names; reopen the archive to review fresh names after a concurrent edit. Storage failure with an unchanged revision retains the whole selection for retry. Success is reported only after commit, with the actual imported count.

After success, the first selected map opens using the existing first-open fit mechanism, displaying only that map's objects/background. Its ID has no previous camera; all other map viewports stay in memory. Cancelling or a failed import leaves the current map and camera unchanged. Repeated imports are independent batches with fresh IDs and newly reserved names.

## Names and marker copies

`availableCopyName` compares trimmed names without case and uses the literal **Copy** in both interface languages. `availableCopyNames` reserves names in batch/source order; preview and storage use this same policy. A level keeps its trimmed original name when free; collisions produce `Level 8 Copy`, `Level 8 Copy 2`, etc., checking both the existing project and earlier maps in the batch. Marker duplication always appends the suffix and checks names of placements on the current map. Prefixes are shortened only when required to stay inside the existing 512-character limit; existing names are never changed.

**Duplicate / Дублировать** is available in the saved marker's view card and its own right-click menu in Preparation. The ordinary empty-map context menu retains Add region and the marker-type submenu. Existing dirty-card decisions run before duplication. Every marker kind, including traps, copies type, status, checks, description, tags, color and current-map bindings into a fresh Entity and Placement; check IDs are new and the placement starts unlocked.

The shared card opens in edit mode. The new copy is a movable draft until Save; Cancel leaves neither entity nor placement in IndexedDB. Successful writes use the existing atomic marker save. The position uses a 36-screen-pixel offset converted through the current camera, clamped into the visible map area while reserving space for the card. Narrow layouts use the free strip above the panels. The camera is not moved or fitted. Documents are cloned; existing same-project image Assets are deliberately shared. Editing one document or deleting one placement/map respects the existing reference-preservation rules and does not damage another copy's images. Deleting a placement continues to retain its Entity, as before.

## Align map image

The current-map menu offers **Align map image / Выровнять изображение** only for a background in Preparation. It resolves dirty cards first and enters a clearly labelled tool with Save, Cancel and a short gesture hint. Dragging over empty space, a region or a marker moves only the image placement in map coordinates. Object hit-testing/selection, drawing, vertex editing and object geometry undo/delete shortcuts are disabled. A **Pan view / Перемещать вид** toggle makes the same mouse/touch drag pan the camera; switch back to Move image to continue alignment. Wheel/zoom controls and arrow-key camera movement remain available.

Movement changes only the draft's x/y. Image width, height, rotation, region vertices and marker positions are retained. Cancel restores the stored position. Save updates ImagePlacement x/y, map coordinateBounds and project revision in one transaction, reporting success only after completion. A failed transaction retains the draft and error for Retry. Save/Discard/Continue decisions protect dirty alignment when closing the tool, changing maps/projects or entering Play. Saving/cancelling keeps the camera; Show entire map explicitly fits the displayed image's actual position. Play blocks alignment and restores ordinary view interactions.

## Version and compatibility decision

**IndexedDB 9 / Project 2 / project ZIP 8 are unchanged.** Batch selection, previews, progress and completion counts are UI state, not a new file format. ImagePlacement already owns x/y independently of the camera; export/import already projects and remaps those fields. No new store, field, dependency or migration is needed. Missing legacy image offsets are normalized to zero on read, and archive validation accepts absent x/y as zero; malformed present values remain invalid. The next successful write emits explicit coordinates. UI drafts, tools and viewports stay outside archives. Existing ZIP 1…7 compatibility remains.

1. Start `npm run dev`. In each interface language, create a project with at least three maps, including repeated names that differ only in case. Add a background, description image, two regions and a trap with checks and bindings to both regions on the first map. Align its background, save, then export the project ZIP.
2. Open another project with its own context and an existing map of the same name. Choose Import levels: all checkboxes start checked in source order. Clear selection (confirm disabled), check just one and inspect its final name/exclusion warning. Cancel; verify the original map/view remain. Repeat with one, several and all maps; inspect the selected count and final names before confirming. Repeat the same batch: names gain Copy / Copy 2 without replacing maps. The first selected level opens, and previous maps retain their camera. Inspect trap checks, shared entities/images, region links and unchanged target context. Simulate a storage failure: no part of the batch remains and the same checked selection is retryable. Export/import the resulting project and reload.
3. Duplicate a saved marker from its card; move it, then Cancel. Repeat from the marker's right-click menu and Save. Change its status/text; verify the original is unchanged. Delete one placement and inspect the other marker's images.
4. Zoom/pan, enter Align map image, and drag from an area covered by an object. Verify objects stay fixed and only the background moves. Toggle Pan view and drag; switch back. Cancel, then repeat and Save. Use Show entire map; switch away/back and reload to verify alignment persists.
5. Change a card/alignment draft, then attempt another map/project/mode or Import levels. Try all three draft decisions. In Play verify import, duplication and alignment are unavailable. Export the updated project and restore it as an independent copy; inspect imported levels, marker copies, links and images.

Drafts and viewport/undo history remain page-memory only. Supported attachments are the image Assets already supported by this version. Ordinary project reload retains the existing first-map behavior. There are no new external services or bundled adventure materials.
