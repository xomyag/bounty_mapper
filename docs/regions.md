# BM-005: polygon regions

Current UI-01 rule: the whole outline moves only while its card is in edit mode. Movement is part of the common Save/Cancel draft; the database is unchanged until Save. In view mode or with the card closed, dragging inside a region pans the camera. Vertex editing and creation retain their previous rules. See [controls and draft history](ui-controls.md).

BM-005 and fixes passed manual acceptance on 2026-10-09. Accepted behavior includes moving vertices during creation, double-clicking a handle to remove it without simultaneously finishing the outline, and keeping the palette open after choosing a color. Outside click or Escape closes it. Since BM-006, color remains in the shared card draft until Save; the separate properties panel and Apply were replaced by one card.

`Region` in `src/domain/region.ts`: `id`, `mapId`, `vertices: {x, y}[]`, `order`, `number`, `title`, `color`, `fillOpacity`; BM-006 also adds `titleCustomized`, rich JSON `gmNotes` / `playerDescription`, `checks`, `tags`. Number is a positive safe integer; title is nonempty; color is hex RGB; opacity is 0…1, default 0.4. Canvas labels are constructed as “number. title”; no duplicate label is stored. Cards, text saving and migrations are documented in [region-details.md](region-details.md).

Geometry is a closed simple polygon; the final edge does not duplicate the first vertex in the array. At least three distinct vertices, nonzero area and finite coordinates are required. Intersections, touching nonadjacent edges and overlapping edges within one polygon are forbidden; adjacent collinear vertices are allowed without backtracking along an edge. Different regions may fully overlap. `order` determines display order; newer regions sit above older ones. Selection uses the visible outline/fill; BM-008 subsequently adds navigation to select obscured regions.

Coordinates are independent of the image and camera. Stage applies one camera to all shapes. Input converts screen→world; moving the outline adds one offset to every vertex; moving a handle changes only one vertex. Edge insertion projects the pointer onto the segment. Handles, selection stroke and label size stay constant on screen during zoom. Replacing an image preserves outlines. Removing the image leaves the map and regions editable.

Creation, pointer preview and drag preview are temporary UI state. Draft vertices can move and be deleted by double-clicking a handle, down to an empty outline. Three vertices and valid geometry are required only on completion. Draft edits write neither database nor history; they belong to one creation operation. Editing a draft after a write failure clears the old retry so stale coordinates cannot be saved.

Double-click uses the browser's dblclick event. The first mousedown records whether an existing handle was under the pointer: double-click on it removes that vertex; on the background it adds the final new vertex and finishes. The second click with detail=2 adds no vertex. This preserves double-click completion even when the first click creates a handle at that point. In saved-region vertex mode, double-clicking a handle executes the ordinary undoable delete command, retaining at least three vertices and valid geometry. Enter/Done validate and save; Escape discards the draft. Export reads only saved domain data. Failed creation retains draft vertices in memory; failed changes retain previous database geometry and allow retry. Form field input survives a failed apply.

`RegionRepository.save` atomically replaces a map's region list and increments Project.revision. It checks map/region ownership, ID collisions and revision. Any write failure rolls back both list and revision. `ProjectSession.mutateProject` serializes commands with images and context; success is published after transaction.oncomplete. A read failure disables changes so an empty UI cannot overwrite saved regions. Explicitly reopening even the same projectId rereads map and regions.

`RegionSession` keeps before/after snapshots of the last 100 completed operations. A vertex drag saves one operation on release; creation/deletion also support atomic undo/redo. Since UI-01, whole-outline movement first enters draft history (one drag — one undo); Save writes its final geometry with card fields and adds it to shared map history. Existing snapshots receive current fields so geometry undo cannot restore stale text. A failed write does not advance history. A successful new command clears redo. Reload and map switching/reopening clear history. Camera, selection, vertex mode and draft are not project history or archive data.

In BM-007, deleting a region atomically removes its ID from related placements' regionIds, retaining other bindings, markers and entities. Shared map history contains region/marker changes; undo restores bindings. Changing entity status after region deletion does not erase historic links. Related markers are computed for the card, not stored inside Region. See [markers.md](markers.md).

Editor limits: 2048 regions per map, 512 vertices per region, absolute coordinates at most 1e9; tolerance for distinct points and nonzero area is 1e-8. Archives additionally cap a project at 2048 regions, 65536 vertices total and the existing 4 MiB JSON limit. These limits bound validation cost for an untrusted archive. Regions need not lie inside the image.

Migration: IndexedDB 2→3 adds `regions` with id key and nonunique mapId index. Existing records are not rewritten; old maps receive an empty region list. Project.schemaVersion remained 1 because Project structure did not change. ZIP v2 adds required regions; v1 import validates the previous strict structure and explicitly creates regions=[] in memory. Region IDs and mapId references are remapped with all other data; the same copy transaction includes regions. See [backup-format.md](backup-format.md).
